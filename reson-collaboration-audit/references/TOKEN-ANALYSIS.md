# Token 多维账本与问题诊断

仅在用户要求 Token 用量分析或综合复盘已有可用计量证据时加载。分析只消费授权范围内的既有事件，不自动扫描会话目录、读取私人历史、采样、安装计量依赖或补写历史事实。

## 1. 先回答哪些问题

1. 哪些日期和时段消耗最多？是任务数量增加，还是每次用量观察变大？
2. 哪些模型消耗最多？同一工作类型内的差异是否仍存在？
3. 哪些工作类型消耗最多？有没有与失败、返工、重复读取或必要审查关联的证据？
4. 哪些消耗有交付价值，哪些有证据支持可避免？下一项改进如何验证而不牺牲质量？

先交代日期、时区、包含的会话／执行者、数据来源、缺失范围和用量口径，再给排行。没有事件不能填零；没有同类任务对照不能声称某模型更省、更快或应被替换。

## 2. Canonical 用量事件

```json
{
  "schema_version": 2,
  "event_type": "token_usage",
  "event_id": "usage-observation-001",
  "session_id": "redacted-stable-session-id",
  "root_task_id": "task-001",
  "actor_id": "root",
  "timestamp": "2026-10-10T09:30:00+08:00",
  "provider": "provider-a",
  "model": "exact-model-version",
  "work_type": "coding",
  "usage_mode": "delta",
  "measurement_kind": "reported",
  "input_tokens": 1000,
  "output_tokens": 200,
  "cached_input_tokens": 300,
  "cache_creation_input_tokens": 0,
  "reasoning_tokens": 50
}
```

字段与边界：

- 计量主键为 `(session_id，actor_id，usage_id 或 event_id)`；无会话标识时允许明确的 `root_task_id` 代替会话范围，要求它在输入集合中全局唯一。`actor_id` 必须存在；`unbound-root` 不提供有效身份。ID 只表达真实用量观察，不为缺失的历史事件生成新 ID。
- 相同主键、相同计量内容的交付重放只计一次；时间以 UTC 归一化比较。计量内容冲突时排除该身份的所有版本，计入覆盖缺口，不能选择较大值或最后一版。发生身份是采集方契约，不由聚合器认证。
- 只计 `token_usage`，不叠加 `model_input_usage`、技能文本量、工具载荷、子代理总结或根任务总量。根／子执行者各自的实际用量可以合计，但父记录不得同时包含已单列的子用量。
- `input_tokens/output_tokens` 都必须是非负整数，不接受布尔值、字符串、浮点数或缺失。`usage_mode` 只接受 `delta`；累积读数必须先在同一计量范围内标准化为增量。旧 canonical 事件未写 `usage_mode/measurement_kind` 时按 `delta/reported` 解释，报告说明历史默认；不得将不明来源的原始计数直接冒充 canonical。
- `measurement_kind=reported` 表示宿主／提供方上报的用量，不表示账单已核验；`estimated` 单独成账，不能与上报值合成一个“实际总量”。不能把技能文本 Token 估算包装成模型用量。
- **统一口径**：输入总量已经包含缓存读取和缓存创建，输出总量已经包含推理 Token；总量仅为 `input_tokens + output_tokens`，不能再加子集。来源若把未缓存输入、cache read、cache write 分列，必须先按其文档归一化，不能直接把未缓存输入映射成此处的输入总量。
- 可选的缓存／推理字段缺失保持缺失；不得填零。已知缓存读取＋创建不得超过输入总量，推理不得超过输出总量；没有独立字段时不从输入总量倒推。
- `provider/model` 保留来源中的准确标识与版本，不按本轮默认模型补历史模型，不把不同版本合并。缺失模型展示为 `unknown`；缺失 provider 也展示为 `unknown`，不据此断言平台相同。
- 时间必须是带时区 ISO 8601。使用**用量被观测的时间**归属日期和时段，不按文件修改时间归属，也不按任务持续时间拆分 Token。时间未知时：无窗口筛选计入 `unknown` 时间分组；有窗口筛选则不能证明命中范围，排除并报告。
- 工作类型只消费明确标签，不能根据工具名、文件扩展名或模型猜测任务性质。未经授权不读取提示词正文进行分类。`work_type` 缺失或非法归入 `unknown`；原始缺失字段不被回写。

工作类型枚举：`coding` 开发、`debugging` 排障、`testing` 测试、`review` 审查、`research` 调研、`writing` 写作、`data_analysis` 数据分析、`planning` 规划、`operations` 运行操作、`skill_maintenance` 技能维护、`other` 明确的其他工作。混合任务按用量观察标注实际工作；只有根任务总计时不强行拆分，保留未知。标签是来源声明，必要时核验而不是把它当作已认证事实。

## 3. 确定性计算

在技能目录执行，默认只向 stdout 输出：

```powershell
python generate_final_report.py --input <events.jsonl> --strict --token-start 2026-10-01 --token-end 2026-11-01 --token-timezone "+08:00" --token-bucket-hours 6
```

- 窗口是 `[start, end)`；日期形式表示所选固定偏移的当天零点，也可给带时区的精确时间戳。结束日期不包含；一整天用当天至次日，不用 `23:59:59`。
- 默认固定时区 `+08:00`，分桶宽度 1 小时；可用 1／2／3／4／6／8／12／24 小时，桶边界从当地零点开始。只支持固定偏移，不声称支持 IANA 时区或夏令时。
- **这些 `--token-*` 参数只筛选 `token_analysis`，不筛选其他运行／协作指标。** 如需全报告同一时间范围，须先提供已经按相同范围准备的完整事件集合，并保留范围和冻结证据；不能把未筛选的运行指标与筛选后的 Token 作因果比较。
- 跨文件、跨会话可用显式授权的事件目录，但不能将原始快照、标准化事件和聚合报告混放并重复计数。目录内只放本次已选证据；不扩大读取范围。
- `--strict` 对输入覆盖缺口或 `token_analysis.status=partial` 返回 2；不存在 Token 事件时为 `unavailable`，选定窗口无事件且无缺口为 `empty_window`，不因此让原有非 Token 审计失败。若任务要求实际 Token 分析，这两种状态仍不能交付为已完成用量分析。
- 输入解析失败、非法计数、累积事件、身份冲突及未知模型／工作类型／时间均披露，不将错误伪装为“无消耗”。错误身份被排除后的总量只代表可用观察子集。
- `--output` 仍需用户要求保存并指定位置；它输出 JSON，不生成或自动归档 MD／HTML。

新扩展保持外层 `schema_version=2/metric_semantics_version=2`，独立使用 `token_analysis.semantics_version=1`：

| 路径 | 含义 |
| --- | --- |
| `scope` | 时区、桶宽、起止边界、Token-only 过滤语义 |
| `coverage` | 原始用量事件数、唯一身份数（含可识别的非法身份）、重放数、冲突／非法身份数、窗口排除数、缺失时间与未知模型／工作类型数、错误分类 |
| `reported/estimated.totals` | 两套互不混合的总量、观察数、已知根任务数及平均每次用量观察 Token |
| `by_date` | 当地自然日汇总 |
| `by_time_bucket` | 带日期和时区的连续时间桶；只输出有观察的桶 |
| `by_time_period` | 跨日期合并同一日内时段，末桶可标为 `24:00` |
| `by_model` | 按 provider＋准确模型标识汇总，降序排列 |
| `by_work_type` | 明确工作类型汇总，未知单列 |
| `by_model_work_type` | 模型×工作类型交叉汇总，定位消耗集中单元 |

每个分组都包含 `input_tokens/output_tokens/total_tokens/usage_count/root_task_count/share/tokens_per_usage`。每个维度分别对同一账本守恒，**不同维度的总量不能相加**；根任务可能跨多个分组，分组根任务数也不能相加成总任务数。`tokens_per_usage` 的分母是用量观察，不保证等于模型请求数；累积采样间隔变化会影响它，不能用它冒充单次调用成本。缺少用量观察的账本 Token 总量为 `null`，有真实零用量观察时才为 `0`；零总量占比为 `null`。

可选字段只有该账本／分组全覆盖时才给总量；同时提供 `*_observed_sum` 和 `*_coverage_count`。部分覆盖的缓存观察值不表示总缓存量。所有 `share` 都以**同一种 measurement_kind、同一选定窗口的 Token 总量**为分母，未知分组也在分母内，防止隐藏缺口抬高占比。

保存的 JSON 可用 `python scripts/validate_agent_audit.py <report.json>` 检查新扩展的结构和分组对账。验证器不认证账单、来源身份、标签真实性、模型选择效果或因果判断；必须绑定已授权输入和快照证据。

### 现有 Codex 适配器

`standardize_codex_rollout.py` 保留 `turn_context.model`、可用的 `model_provider` 和脱敏后的稳定会话 ID；模型归属是运行上下文声明，不等于独立逐请求认证。`--work-type research` 等参数仅用于**用户已明确分类的同质输入**；混合输入不要整体贴标签，也不能按报告想要的结论贴标签。

累积总量单调且有前值时做差；首次观察或计数重置时只使用真实的 `last_token_usage`，缺失／非法时保留缺口而非补零。第一条 last usage 只覆盖该次已知观察，不证明窗口此前的全部消耗；跨窗口差分以结束观察归属，不按窗口边界插值。模型切换间隔可能包含未逐次观测的调用，精细跨模型对比需额外核验采样范围。只在同口径有真实字段和可比前值时保留缓存／推理增量。

该适配器不处理 Pi 或其他宿主的原始会话格式。其他宿主需按自己的已核验字段合同提供 canonical 事件；不能仅把原始文件喂给聚合器就声称原生会话已统计。

## 4. 主要问题与改进建议

综合报告增加集中摘要，不让读者从指标表自行猜原因：

- 列出影响最大的**已证实问题**，没有证据就少列或写“尚不能确定”。每项绑定稳定 `F-xx`、根任务／会话和时间范围、证据位置、来源核验状态、发生数／暴露分母、实际影响、归因边界及替代解释。
- 问题与证据缺口分列。高 Token、高缓存量、子代理占比或深夜集中消耗只是观察，不自动成为问题；必要审批、独立审查和安全停止不算浪费。
- Token 影响只有在明确的用量事件与失败／返工范围可匹配时才计算；不能把同一任务总量全部记为某个故障的额外消耗。多项问题可能共享同一批用量，不能叠加为“可节省总量”。时间影响只用实际时长；没有价格和计费规则不估算金额。
- 每个问题连接 `R-xx`，给出具体动作、SYSTEM／USER 分工、实施层、所有者、依赖及授权、预期方向、比较样本与质量／安全护栏、验证和停止／回滚条件。建议不表示已经修改；MD／HTML 的建议仍由同一个 canonical manifest 生成。
- 优先级先看安全、数据完整性与任务阻塞，再看可核验的返工／重复消耗；影响、成本和可逆性分别描述，不制造无基准综合分。
- 仅从建议队列中选择**下一项唯一实验**。验证使用同工作类型、相近难度、相同模型版本／采样口径和可比来源；同时核对任务验收、错误率、用户介入及 Token。省 Token 但质量下降或把工作转交用户，不算改善。

可检查的故障链与最小实验（都是候选，不是默认结论）：

| 候选问题 | 必要证据 | 可能改进与验证 |
| --- | --- | --- |
| 重复上下文载入 | 同范围重复载入回执＋可比模型用量，排除必须的重读 | 按需加载；比较同类型任务总用量和验收，不能拿技能文本量当已省账单量 |
| 无新证据重试 | 稳定错误签名、重试证据和对应用量；区分运行时内部重试 | 修复单一错误源／前置只读探针；核对同签名复发与质量 |
| 长任务返工 | 明确返工原因、阶段事件和可匹配用量；排除新增需求 | 先明确输入／验收；比较同类任务返工和验收，不一味缩短答复 |
| 模型与工作不匹配 | 模型×工作类型用量、任务难度、质量和实际时间 | 小范围同类对照；只有质量不降才能讨论模型路由，不直接改全局配置 |
| 委派上下文冗余 | 真实子代理用量、传入范围和产出价值 | 最小任务包；保留必要独立审查，比较总量与验收，不只看子代理占比 |
| 工具／连接器失效 | 原生错误、同签名频次、受阻任务和实际时长 | 修复接口／路径或受保护降级；按故障合同停止，不新增盲重试 |
| 时间或标签覆盖不足 | unknown 观察数及其 Token 份额、非法事件和冲突 | 在已有授权范围内完善未来计量；不能反填历史或把计量完善当收益 |

## 5. 失败模式与验收

关键失败模式：空证据、真实零用量、畸形字段／布尔计数、累积值误加、缓存和推理二次计入、同一记录重放、相同身份冲突、跨会话／执行者局部 ID 碰撞、缺失／无时区时间、跨日时区边界、结束边界重复、模型或工作类型未知、混合任务错贴标签、窗口指标错配、输入读取失败及部分来源覆盖。

确定性测试覆盖日期／时段守恒、模型与工作交叉守恒、缓存子集、分离估算、身份去重／冲突、缺失与非法输入、窗口边界、CLI 严格退出、流式／列表结果一致、JSON 验证器对账，以及 Codex 标准化→聚合最薄端到端。工作标签真实性、必要性、收益归因和真实宿主账单完整性仍需实际审计证据，测试不能替代。
