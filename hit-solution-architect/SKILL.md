# 医疗数字化解决方案架构

## 边界与交付原则

- 先明确业务问题、风险和决策，再选择系统、产品和技术。
- 本技能负责技术方案、既定战略下的技术蓝图和架构评审；战略取舍、商业模式、投资组合和高管决策由 `hit-digital-strategy-partner` 主导。混合任务按“战略判断—技术架构—文档或演示制作”衔接。本技能可计算技术 TCO 和实施成本驱动，但 ROI、预算取舍和投资推荐由战略技能主导。
- 只有获得当前、可核验且允许使用的产品或案例材料时，才做厂商或产品映射；否则输出厂商中立方案、证据缺口和验证计划，不凭记忆补齐。
- 将客户确认事实、外部证据、项目假设、建议和待决定事项分开；不以产品部署推断业务成熟度，不承诺未经验证的临床效果、性能或收益。
- 在适用的安全、数据和证据硬门槛内，用户指定的范围、格式和深度优先，不为凑齐模板生成无关章节。

## 任务路由

先选择一种交付模式，再只启用适用模块。模式定义和最小成果见 [references/delivery_profiles.md](references/delivery_profiles.md)。

| 模式 | 适用任务 | 默认启用 | 默认不启用 |
| :--- | :--- | :--- | :--- |
| 架构快评 `brief` | 单点判断、方案初筛、关键风险识别 | 结论、证据缺口、前三风险、下一步验证 | 迁移、TCO |
| 售前方案 `proposal` | 需求响应、解决方案、PoC设计 | 需求映射、目标架构、NFR、差距与承诺边界、验收 | TCO按需 |
| 技术规划蓝图 `blueprint` | 技术蓝图、项目依赖、分期技术路线 | 能力差距、技术项目包、依赖、治理、架构视图 | 商业战略结论 |
| 详细架构 `design` | 应用、数据、集成、部署、安全、容灾设计 | 架构视图、接口契约、容量、SLO、运维、测试 | TCO按需 |
| 架构评审 `review` | 对既有方案形成正式审查意见 | 依据、问题分级、判定、整改、例外记录 | 新建完整方案、TCO |

迁移仅在替换、升级、割接、并轨或退役任务中启用；技术 TCO、实施成本和可审计收益变量仅在用户要求或决策确实依赖量化时启用。涉及 ROI、预算取舍或投资推荐时衔接 `hit-digital-strategy-partner`。

## 输入合同与阻塞判断

至少确认或从材料中可靠推断：决策问题、技术范围、交付模式。按 [templates/input_contract.md](templates/input_contract.md) 建立输入表。

- 能可靠推断的内容：继续执行并记录来源。
- 不改变架构方向的未知项：列入信息缺口和取证计划，不阻断初稿。
- 会改变司法辖区、临床安全、数据使用、系统边界、停机策略或对外承诺的未知项：只提出一至三个阻塞问题，未确认前不输出确定性结论。
- 没有客户数据时保留明确编号的假设或取数项；不得用行业经验比例、示例值或固定周期替代项目证据。

## 医疗安全与数据门禁

开始外部检索、并行委派或详细设计前，确认或从材料中可靠推断适用地区、是否跨境、资料密级、患者数据状态、外部使用授权、临床影响等级和交付成熟度。公开、低风险快评可先记录适用性假设；只有未知项会改变设计、安全或合规结论时才阻塞。

- 含可识别患者数据或未经授权的内部、机密材料时，停止外部检索和委派，只处理最小必要且已脱敏、获授权的内容；必要时请用户提供合规版本。
- 已授权敏感材料仍只作最小必要处理；获准用于当前任务不等于获准发送给外部工具、外部检索或子代理，缺少单独授权时不得传递。
- 司法辖区或跨境路径未明确时，不给出确定性合规结论，只列适用性假设和需法律、合规负责人确认的事项。
- 直接影响诊断、治疗、用药、检验结果或临床连续性的方案，必须读取 [references/clinical_safety_cutover.md](references/clinical_safety_cutover.md)，覆盖临床风险清单、降级流程、数据核对、切换前继续实施/暂停实施决策和回退；临床负责人签字是生产切换前门槛，不是形成初稿的前置条件。
- 临床 AI 方案必须说明预期用途、输入边界、人类监督、本地验证、性能边界、漂移监测、故障降级、版本回退、不良事件、责任主体，以及医疗器械或临床研究属性；伦理审查和知情同意按适用性纳入。

## 证据规则

按 [references/evidence_governance.md](references/evidence_governance.md) 建立主张级证据台账。

- 政策、标准、目录、产品版本、价格和兼容状态等时效性信息，优先核验当前正式的一手来源，并记录资料日期、地区、版本和适用条件。
- 厂商材料只能证明厂商声明；临床效果、客户成效、合规结论和兼容结论必须由对应原始证据或项目测试支持。
- 来源冲突时并列差异、判断证据强度并保留替代解释；无法联网或取得正式来源时明确降级为“待核验”，不得形成承诺。
- 每个实际量化主张记录数值或区间、单位、来源、资料日期、适用地区和口径；假设还要记录假设编号及敏感性范围。

## 执行流程

1. 选择交付模式和条件模块，记录交付状态：工作稿 `draft`、审阅稿 `review` 或可提交稿 `release`。
2. 执行输入、数据和临床安全门禁，区分阻塞问题与可后补信息。
3. 按所选模式与已有材料裁剪现状视图和证据台账；`brief`、`review` 只检查支撑当前判断所需的流程、边界、接口、数据、运维责任和风险。
4. `proposal`、`blueprint`、`design` 定义相应深度的目标能力和非功能要求；每项 NFR 写明指标、单位、负载或适用范围、测量方法、责任人和验收阈值。
5. `proposal`、`blueprint`、`design` 设计相应深度的目标架构，标明系统责任、数据权威源、接口契约、部署边界、关键依赖、故障降级和可观测性；`review` 评估已有架构，不重建无关内容。
6. 仅对适用链路使用 [templates/architecture_traceability.md](templates/architecture_traceability.md) 建立“业务问题—能力—系统—数据—接口—NFR—验收”追溯关系；`brief` 保留最小证据链即可。
7. 按需制定迁移、双轨、数据核对、切换、回退、停机和退役路径；按需建立技术 TCO、实施成本和可审计收益变量，ROI结论由战略技能承接。
8. 对关键假设、单点故障、供应商锁定、临床安全、合规、容量和割接风险做反证检查，保留替代方案与剩余风险。
9. 三个以上独立技术面可并行验证；涉及受限材料时不得委派。整合时统一事实口径、编号、边界和责任。
10. 按交付模式完成成果；未经用户授权不发送、发布或写入外部系统。

## 图示与交付

- 关系简单时用表格或文字；复杂依赖、数据流、部署或切换关系用最少必要的架构图。
- 详细架构通常至少选择系统上下文、应用/数据流、部署/容灾、迁移状态中的一个或多个视图；每张图标明范围、边界、责任和关键假设。
- 架构评审使用 `blocker / major / minor / observation` 分级，并给出“通过 `pass` / 附条件通过 `conditional_pass` / 不通过 `fail`”及整改证据要求。
- 物理交付为 Word、PPT、PDF或其他格式时，继续使用对应文件技能完成渲染和视觉验证；本技能负责内容与技术质量门槛。

## 发布前质量门禁

工作稿允许受控占位符，但必须集中在信息缺口、假设或取数计划中。审阅稿和可提交稿不得在技术承诺正文保留占位符；可提交稿还必须完成主张证据、临床安全、产品承诺和项目可执行性的人工复核。

若当前环境可执行脚本，在技能目录一次运行：

```bash
QA_TARGET_FILE=/absolute/path/to/solution.md
QA_PROFILE=proposal
python3 scripts/qa_runner.py "$QA_TARGET_FILE" --profile "$QA_PROFILE" --stage release
```

将 `QA_PROFILE` 设为本次选择的 `brief`、`proposal`、`blueprint`、`design` 或 `review`。按任务增加 `--require migration`、`--require tco`、`--require clinical-safety` 或 `--require evidence`。自动检查无硬错误只代表自动门禁通过，不代表人工复核完成或可以对外发布；仅在方案逻辑、产品适配、承诺风险和项目可执行性复核已实际完成并留痕后增加 `--review-complete`，不得把该参数当作复核本身。维护技能资源时运行 `python3 scripts/resource_validator.py`。

最终确认：

- 每个模块对应明确业务能力、风险控制或验收目标。
- 架构边界、数据流、接口责任、系统责任和关键依赖可追溯。
- NFR、迁移、临床安全和量化模块只在适用时启用，但一经启用必须达到对应完成门槛。
- 产品比较基于版本化证据和项目要求，明确已具备、需配置、需开发、需合作伙伴、未验证和暂不支持，不设置排他参数。
- 交付状态、剩余风险、待决定事项和最终责任人清晰。
