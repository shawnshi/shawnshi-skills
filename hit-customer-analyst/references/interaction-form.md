# 四模式交互表单 v2.7.0

## 通用规则

- 先读取用户原话、附件和既有成果；已明确的信息直接采用，不重复询问。
- 用户只看到会前速览、标准拜访包、战略客户包、一封信，不询问route/depth。
- 只问会改变主体、模式、关键结论、内部授权或外发事实的阻塞问题。
- 每轮最多3个简短问题；提供“暂不清楚/按现有信息继续”。
- 未回答不视为同意；可按假设继续时建立H主张并说明影响。
- `refresh`只作后台动作，不作为第五个选项。
- 外发内容、关键身份冲突和会改变主推进动作的冲突必须确认。

## 工具调用前 intake 预检

在创建客户工作区、生成检索计划或发起公开/内部检索前，先把用户原话中同一高影响字段的每次出现保留为独立候选，并运行：

```bash
python3 scripts/preflight_intake.py <intake.json> > <intake-gate.json>
```

输入契约见 `schemas/intake-preflight.schema.json`。主体、机构范围、拜访对象姓名/职务/层级、会议状态、会议时间、项目范围、收件对象、拜访目标、最小动作、签署人和发送渠道不得在抽取时静默覆盖。等价候选可以自动合并；不同候选只有绑定本轮用户确认后才能选择，模型不得以来源顺序、检索结果偏好或“更合理”为由自行裁决。

- `status=blocked`或退出码3：只展示返回的阻塞问题并停止；不得初始化、生成查询、联网或访问内部资料。
- `status=ready`且未超过`expires_at`：初始化和研究计划都必须传同一原始输入`--intake-input <intake.json>`，由各命令在任何写入/检索前重算状态、`input_sha256`和时效；不接受脱离原始输入的自报ready或手改回执。
- 用户补充、更正或新增任何候选后：原回执立即失效，使用完整新输入重跑预检。
- 预检回执仅表示可以开始初始化或检索，不代表研究计划完整、证据已核验、成果已审核或`ready_for_use=true`。被阻断的预检必须保持零业务副作用：输出根目录、候选目录、查询计划和四个运行机器文件均不得新建或改动。

`meeting_status`只允许`confirmed|tentative|none|unknown`，并使用候选`status=asserted`；它表达“会议是否成立”，不表达具体时间。会议时间另用带时区的`start/end`结构；时间待定用候选`status=explicit_unknown`和`value=null`，不得补成默认日期。`confirmed`即使具体时间待定也表示已有需执行准备的会议；`tentative`保守按账户规划继续，待认证宿主核验确认后才转会议准备；`none/unknown`且无确切会议时间时按账户规划。`none/unknown`与确切时间并存属于跨字段冲突，必须澄清；同一字段多时间冲突仍阻断。结构化输入只保留完成消歧所需字段和来源定位，不复制患者信息、私人信息或未获授权的客户内部内容。

### 最小输入

| 模式/分支 | 预检可继续所需最小业务输入 |
|---|---|
| 会前速览、标准拜访包 | 客户主体；拜访对象姓名/职务/层级至少一项；目标；最小推进动作。会议时间不是必填，未知时不得猜测 |
| 战略客户包－已确认会议 | 客户主体；`meeting_status=confirmed`（具体时间可未知），或在未提供状态的兼容输入中有唯一确切会议时间；对象姓名/职务/层级至少一项；目标；最小推进动作 |
| 战略客户包－账户规划 | 客户主体；战略问题；经营周期；最小推进动作。`meeting_status=tentative|none|unknown`可明确选择该分支；未提供任何可信会议事实时也默认该分支 |
| 一封信 | 客户主体；收件角色；信件场景；目的；期望动作；签署人/稳定签署角色；发送渠道 |

内部检索另要求项目和授权契约；上述最小输入只表示intake可进入后续步骤，不表示证据、审核或外发门禁已通过。人物姓名、项目范围、会议时间等非必填信息若出现冲突，仍必须先消歧。

## 模式确认

只有用户成果无法唯一判断时问：

“这次希望得到哪一种成果？”

1. 会前速览：1页快速简报；
2. 标准拜访包：研究摘要＋完整交流策略；
3. 战略客户包：客户全景＋机会与投入判断；
4. 一封信：研究支撑的内部审核稿。

若用户同时要求多项，选择最终业务用途最完整的模式。例如“先更新人物，再设计下周拜访”选标准拜访包，人物更新作为后台刷新；“更新研究并写邀约信”选一封信。

只要求结构化客户研究时仍映射到四模式：快速摸排或1页结论选会前速览；常规研究选标准拜访包；客户全景、重大机会或投入取舍选战略客户包。会前速览或标准拜访包没有已排定会议时，可以后续交流的角色层级、验证目标和最小动作填充业务字段；战略客户包没有会议时改用account_planning，以战略问题、经营周期和最小动作组织成果。不向用户暴露`research_only`或`strategy_variant`。

## 会前速览

最多1轮，只处理优先级最高的阻塞点：

1. 主体、院区或部门无法唯一确认；
2. 拜访对象/层级完全不清楚；
3. 会议时间和剩余时长未知且会影响是否来得及；
4. 目标或最小推进动作完全缺失；
5. 具名人物身份存在冲突。

已知则直接执行。无需用户补全合作历史、存量系统、竞对或完整预算。交付1页正文；若关键事实来不及复核，标明阻塞和`ready_for_use=false`。

## 标准拜访包

最多2轮。

第一轮最多3题：

1. 拜访对象、职务/层级、时间和预计会长；
2. 主要目标及会议结束时最小可接受结果；
3. 是否有获授权的内部背景、必须携带的材料或需避免话题。

第二轮只在以下情况出现：

- 人物、采购、合作事实存在高影响冲突；
- 机会资格会实质改变议题或是否推进；
- 参会分工、材料授权或承诺边界缺失；
- 用户主动要求确认。

第二轮展示不超过8条发现、5条缺口、BANT/采购时序/竞争位置、建议`win/conditional_win/monitor/no_go`和一个主动作，再只问阻塞问题。

## 战略客户包

通常2轮。

先抽取`meeting_status`，再派生内部字段`strategy_variant`：`confirmed`为`scheduled_visit`，具体时间可待定；`tentative|none|unknown`为`account_planning`。未提供状态时，唯一确切会议时间可兼容派生`scheduled_visit`，否则默认`account_planning`。`none/unknown`与确切时间并存必须澄清。拜访对象和拜访目标本身不证明会议成立。用户无需理解内部字段，也不得为继续流程要求用户虚构会议对象、时间、参会人或材料。

第一轮确认：

1. 客户/项目/院区范围和经营周期；
2. 本次需要决定的问题：进入、加码、维持、调整或退出；
3. 可使用的内部项目、产品、案例和竞争资料授权。

第二轮确认：

- 关键决策结构和替代解释；
- BANT、采购时序、竞争位置；
- win/no-go、投入强度及停止条件；
- 未来30/60/90天主动作、owner和日期。

用户不知道预算或决策角色时不要求编造；保留缺口并转为验证计划。

只有`scheduled_visit`才补充拜访对象/层级、目标、最小结果、议程、参会分工和材料授权。`account_planning`只要求战略问题、经营周期和最小推进动作；利益相关者未知时按正式角色层级形成验证计划，不把未知姓名变成阻塞项。

## 一封信

先判断是否属于[高风险信件](business-modes.md#一封信)。普通感谢、通知、材料转发或无关键事实的通用文案转普通写作，不加载本技能。

最多2轮，优先补齐：

1. 场景；收件对象（姓名或明确称谓）、角色/身份和确认状态；
2. 目的、希望对方采取的动作；
3. 签署人、发送渠道和是否涉及金额/排期/效果/资源/案例等承诺。

完成内部稿后进入pending。审核必须取得可追溯到真人和稳定角色/账号的approver；审核超时不自动批准。审核通过不等于发送授权。只有用户再次明确要求“生成外发版”时才生成纯净外发文件，永不发送。

## 既有成果与后台刷新

优先通过用户给出的报告、路径或context_id定位；否则按客户规范名和organization_scope查找。

- 唯一匹配：复用并执行TTL检查。
- 多个匹配：列出最多3个候选，只问一次。
- 无匹配：按当前四模式新建。
- 用户说“更新/刷新”但没有最终成果：沿用该上下文最近的`business_mode`；无法推断时问要哪种最终成果。

用户给出的新截止日只作为目标截止日。证据真正写入并合并后，才更新成果的evidence_cutoff_date、版本和freshness。

## 内部授权交互

用户选择或隐含需要内部资料时，先检查实际工具和已提供文件。只在缺失时询问：

1. 可访问的tenant/customer/project三重范围；
2. authorization_owner和授权截止时间；
3. 允许的数据集、目录、密级及是否允许形成写回候选。

“你可以看当前目录”“有RAGFlow”“系统已经接入”等表述不足以证明三重授权或连接器可执行。缺任一项时跳过连接器，以公开/用户提供资料继续并透明降级。

## 审核与交付提示

交付前展示：

- 业务模式；旧route/depth只保留在审计附件，不作为用户选项或正文标题；
- 创建、更新、复用和未调用成果；
- `ready_for_use=true/false`及原因；
- 待审核成果、reviewer、review_due_at和阻塞；
- TTL过期或现场必须验证的信息；
- 主动作、owner和due_date。

`closed`只能表述为“本次生成已结束”，不得说成“已审核”“可外发”。

## 会后交互

用户提供拜访反馈时，优先收集：

1. 哪些事实/假设被确认或否定；
2. 客户的明确决定和采购/项目时间变化；
3. 双方行动、owner、due_date和下一次联系；
4. 是否只生成CRM/PIMS候选，还是在满足权限后实际写回。

零散补充不计新的正式交互轮次。写回前必须单独确认目标系统、三重范围和数据所有者批准。
